# 孩子端任务列表 技术方案

> 版本 v1 · 2026-08-22 · 前置：`docs/design/2026-08-22-任务列表-技术方案.md`（家长端任务列表已上线）
> 目标：孩子端从「只有今天那一份」变成「能看到可做的任务并挑一个做」，顺带补上现在没法补做的漏洞。

---

## 1. 现状：孩子端根本不知道有"任务"这回事

`/kid` 三个页面全部绑在 `useTodayPlan()` 上，`planId` 从头到尾没进过 URL：

```
/kid        KidCover  → useTodayPlan()
/kid/quiz   KidQuiz   → useTodayPlan()   ← 做哪份计划是隐式的
/kid/done   KidDone   → useTodayPlan()
```

而 `Today()` 的语义是「**今天**这个日期下 `seq_no` 最大的那份」（`plan.go:93-105`）。这带来三个后果，前两个是实打实的漏洞：

### (a) 昨天没做完的任务，永远补不回来

孩子昨晚做到 6/10 就困了。今天打开 `/kid`，`Today()` 查的是今天的日期，没有就现场生成一份新的。昨天那份 6/10 在孩子端**再也不可达**，永远停在 `doing`。

这不是假想。`seed_demo_plans.sql:15-18` 造的 8/17（6/10）、8/16（3/10）、8/15、8/14 四份未完成任务，现在就卡在这个状态。

### (b) 加餐会把没做完的主任务挤掉

`Today()` 取 `MAX(seq_no)`。如果主任务还是 0/10，家长在家长端点了「加餐」生成 `seq_no=2`，孩子打开看到的就是加餐那份，主任务被挤到不可达。

取最大序号本身是对的（原注释说得没错：加餐后刷新页面不该被扔回已做完的主任务），错在**只有一个出口**，所以它必须替孩子做选择。

### (c) 孩子没有选择权

只有一条路径，没有"做什么"这个概念。

**任务列表恰好是这三件事共同的解药**：把"做哪一份"从隐式推断变成显式选择。

---

## 2. 范围

三个已确认的取舍（本方案的前提）：

| 决策 | 选择 |
|---|---|
| 孩子看到哪些任务 | **只显示"现在能做的"**：今天的 + 没做完的历史任务；已完成的不进列表 |
| 是否拆独立工程 | **不拆**，留在现有前端的 `/kid` 路由下 |
| 已完成的能否重做 | **不能**。想多练走「再来一组」生成新任务 |

### 做

1. 孩子端首页改成**可做任务列表**（今天的 + 窗口内未完成的）
2. `planId` 进 URL，答题和结算页都按 id 定位
3. 新增两个后端接口：可做任务列表、孩子端安全的单份任务详情
4. 定义补做窗口和排序规则

### 不做（YAGNI）

- **历史成就墙 / 翻看做过的任务**。已完成的任务对孩子只剩"我做过"的意义，而这个用一行「今天完成啦 ⭐⭐⭐」就够了。做一个可翻阅的历史列表，等于给 5 岁孩子一个任务管理器。
- **孩子自选学科 / 自选题量**。选题是掌握度引擎的职责，让孩子挑等于让他永远只挑会的。
- **登录、切换孩子**。沿用现有的 `childStore` 单孩子假设。
- **离线答题**。现在就没有，这版不引入。

## 3. 核心设计

### 3.1 `planId` 进 URL（地基改动）

```
/kid                     KidHome    可做任务列表
/kid/task/:planId        KidQuiz    答题
/kid/task/:planId/done   KidDone    结算
/kid/quiz                → 重定向到今天的任务（旧书签兜底）
```

没有 `planId` 的 URL 就无法表达"做哪一个任务"，所以这一步是其它所有改动的前提，必须先做。

顺带拿到三个好处：刷新页面稳定停在同一份任务上；家长可以把某个任务的链接直接发到 iPad；`KidQuiz` 不再依赖"当前是哪天"这种隐式状态。

`start_url` 是 `/kid`（`manifest.webmanifest:5`），已装到 iPad 桌面的 PWA 入口不受影响。`/kid/quiz` 加重定向只是廉价保险。

### 3.2 新接口：孩子端安全的任务详情

```
GET /api/v1/children/:cid/plans/:planId  →  PlanDetail
```

**现在没有这个接口**——按 id 取详情的只有 `GET /plans/:planId/review`，而那个**含正确答案**，是给家长复盘用的，绝对不能给孩子端。

实现只有几行：`loadPlan(childID, planID)` 做归属校验（顺带防越权），然后复用现成的 `s.detail(p)`。`detail()` 产出的 `QuestionDTO` 本来就刻意不含答案（`plan.go:65`），零泄漏风险，也不用新写 SQL。

#### 路由冲突：已实测，不是问题

`GET /plans/today`（静态）和 `GET /plans/:planId`（参数）在同一层级，老版本 httprouter 会在注册时直接 panic。写了个探针测试实际验证：

```
gin v1.12.0，/plans/today、/plans/todo、/plans/:planId、/plans/:planId/review
四条共存，全部分发到正确的 handler。
```

所以不需要退化成 `/plans/by-id/:planId` 这种绕法。（探针验证完已删除，不入库。）

### 3.3 新接口：可做任务列表

```
GET /api/v1/children/:cid/plans/todo  →  []PlanSummary
```

**为什么不复用 `GET /plans?status=`**：

- 需要 `status IN ('pending','doing')`，现有过滤是单值等值，要改成多值
- 需要"补做窗口"这条业务规则，而规则只能有一份，必须在后端
- 家长端要的是"全部历史"，孩子端要的是"现在能做的"，语义不同。硬塞进一个接口，迟早要加一串开关参数

复用 `PlanSummary`（含 `subjects`），孩子端首页正好要显示学科 chip。

```go
// Todo 返回孩子现在还能做的任务：今天的 + 窗口内没做完的。
// 已完成的不返回——重做会把掌握度刷高，那之后所有数据都不可信了。
func (s *PlanService) Todo(childID int64) ([]PlanSummary, error) {
	to := today()
	from := time.Now().AddDate(0, 0, -kidResumeWindowDays).Format("2006-01-02")

	var rows []model.StudyPlan
	if err := s.repo.DB().
		Where("child_id = ? AND status IN ? AND plan_date >= ? AND plan_date <= ?",
			childID, []string{"pending", "doing"}, from, to).
		Order("plan_date DESC, seq_no").Find(&rows).Error; err != nil {
		return nil, err
	}
	return s.withSubjects(rows)
}
```

`History` 尾部那段「取 ids → `subjectCounts` → 回填空切片」（`plan.go:645-665`）抽成 `withSubjects(rows)`，两处共用。不抽的话就是复制 20 行，而且以后加字段容易只改一处。

### 3.4 补做窗口：2 天

```go
// 没做完的任务只在这个窗口内还能续做。
const kidResumeWindowDays = 2
```

**为什么要有窗口，而不是把所有未完成的都列出来**：

任务生成时是按**当时**的掌握度选题的（复习 4 + 易错 2 + 在学 2 + 新知 2）。一份 10 天前的任务，它挑的"新知"现在可能已经学过了，它挑的"复习"可能早在别的任务里复习过了。续做一份过期任务 = 按过时的判断在练习，而且练完还会把掌握度往回带——`Answer` 照样写 `attempts`，引擎分不清这是"补做的旧题"。

选 2 天（今天、昨天、前天）：昨晚困了没做完、今天补上，这是最真实的场景；3 天前的那份，与其补一份过时的，不如做今天这份新的。

**超窗的任务不做任何状态变更**，只是不在孩子端出现。家长端列表照常显示「进行中 6/10」——这是诚实的信息，那份任务确实没做完。

不引入 `expired` 状态：要加迁移、要有人负责写这个状态（定时任务或懒扫描）、还要想清楚写入时机。收益只是家长端少看到几行"没做完"。真堆积到看不下去那天再说。

### 3.5 排序：今天的永远排最前

```
1. 今天未完成的（seq_no 升序：主任务 → 加餐1 → 加餐2）
2. 「补做」：昨天、前天未完成的（日期倒序）
```

按日期倒序天然满足，`ORDER BY plan_date DESC, seq_no` 一条搞定。

**为什么不是"快做完的排最前"**：昨天 9/10 的任务只差一题，做完很有成就感，听起来该置顶。但「每天一份练习」是这个产品的仪式感，主卡片必须稳定地是"今天的练习"，否则孩子每天打开看到的东西都不一样，习惯就建立不起来。补做是附加项，视觉上降一级。

### 3.6 首页布局与三种状态

```
┌──────────────────────────────────┐
│      卢沁一，今天练一练              │
│                                  │
│  ┌────────────────────────────┐  │
│  │ 今天的练习                   │  │  ← 主卡片：全宽、大字、亮色
│  │ 🔢4 📖3 🔤3   一共 10 道题    │  │
│  │        [ 开始 → ]           │  │
│  └────────────────────────────┘  │
│                                  │
│  补做                             │
│  ┌────────────────────────────┐  │  ← 补做卡：矮一半、灰底
│  │ 昨天 · 还剩 4 道  [接着做 →] │  │
│  └────────────────────────────┘  │
│                                  │
│  🌸 我有 12 朵小红花               │
└──────────────────────────────────┘
```

| 首页状态 | 主卡片 |
|---|---|
| 今天有未完成任务 | 那份任务；`done_count > 0` 时文案换成「接着做」+「还剩 N 道」 |
| 今天还没生成任务 | 「开始今天的练习」，点击先 `POST /plans/today` 再跳转 |
| 今天的都做完了 | 成就条「今天完成啦 ⭐⭐⭐」（不可点）+「再来一组 🍬」 |

两条硬约束：

1. **补做卡最多 2 张，没有就整块不渲染。** 5 岁孩子的屏幕上不该出现一个空的「补做」标题。
2. **视觉层级必须拉开。** 让孩子看到 3 张长得差不多的卡片去挑，等于把"选择"这个认知负担塞给他，还会让"今天该做什么"变模糊。主卡片全宽亮色大字，补做卡矮一半、灰底、小字。

### 3.7 生成任务：列表保持只读

孩子端首页**不**懒生成。今天没任务时渲染「开始今天的练习」，点击 → `POST /plans/today` → 跳 `/kid/task/:id`。

沿用家长端已定的口径（任务列表方案 §5.3）：生成任务只有一条显式路径。好处是 `GET /plans/todo` 变成纯读接口，可以随便刷新、预取，不担心副作用。

**对孩子的操作数没有任何影响**：还是一次点击就进答题，和现在的「开始 →」完全一样，只是这次点击背后多了一个 POST。

按钮要处理 pending 态防连点（孩子一定会连点），失败文案「等一下再试试」。

### 3.8 防重做：三层，其中两层已经现成

| 层 | 机制 | 状态 |
|---|---|---|
| 1 | `GET /plans/todo` 不返回 `done` 的任务 → 首页点不进去 | 本次新增 |
| 2 | 直接输 `/kid/task/:id` 且已完成 → `KidQuiz` 找不到 pending 题，自动跳结算页只读展示 | **现有逻辑**（`KidQuiz.tsx:61-65`） |
| 3 | 硬构造 `POST .../answer` → `Answer` 对非 pending 的题只回放结果，不重复计分、不写 `attempts` | **现有逻辑**（`plan.go:499-505`） |

第 3 层意味着"重做污染掌握度"这个风险在后端本来就被堵死了，前端只是不给入口。这条值得写下来，免得以后有人为了"保险"再加一层冗余校验。

「再来一组」（`useExtraPlan`）是想多练时的正规出口，保留不动。

### 3.9 前端数据层：缓存 key 全部要改

| hook | 现在 | 改成 |
|---|---|---|
| `useTodayPlan` | `['plan','today',cid]` | **删除**，三个调用方全改 |
| `useKidTodo`（新） | — | `['plan','todo',cid]` ← `GET /plans/todo` |
| `usePlanDetail`（新） | — | `['plan','detail',cid,planId]` ← `GET /plans/:planId` |
| `useFinishPlan` | 写 `['plan','today',cid]` | 写 `['plan','detail',cid,planId]` |
| `useExtraPlan` | 写 `['plan','today',cid]` | 写新计划的 detail key + 失效 `['plan','todo']` |
| `useGenerateToday` | 写 `['plan','today',cid]` | 同上 |

两个**极易踩的坑**：

**`usePlanDetail` 必须继承 `staleTime: Infinity` + `refetchOnWindowFocus: false`。** 原因注释已经在代码里（`plans.ts:136-137`：答题过程中背后刷新会把当前题重置掉）。换 key 时把这两行丢掉，症状是孩子答到一半题目突然跳回第一题，而且只在网络慢或切后台回来时复现，很难查。

**`useKidTodo` 恰恰相反，不能 `staleTime: Infinity`。** 做完一份任务回首页，列表必须反映新状态。用默认的 30s + `invalidateQueries` 兜住。

`GET /plans/today` **保留**：`/kid/quiz` 的重定向正好要用它来解析"今天该做哪份"，而且它和 `POST /plans/today` 是天然一对，删了 API 反而怪。

### 3.10 iOS 音频解锁：多入口后最容易漏的一条

现在只有 `KidCover.begin()` 里调了 `sound.unlock()` + `speech.prime()`，注释也写明了原因：iOS 的语音和音频必须在用户手势里首次触发，否则被静默丢弃。

改成列表后入口变成多个（主卡片、每张补做卡、再来一组、开始今天的练习），**每一个都必须先解锁**。抽一个统一入口：

```tsx
const enter = (planId: number) => {
  sound.unlock()
  speech.prime()
  nav(`/kid/task/${planId}`)
}
```

漏掉的后果是：从补做卡进去的那次答题全程没有声音。而这在桌面浏览器上测不出来——桌面没有这个限制，只有真机 iPad 才暴露。

## 7. 取舍与风险

| 项 | 说明 |
|---|---|
| 补做窗口写死 2 天 | 常量，要改改代码。不做配置界面。 |
| 超窗任务在家长端永远显示"进行中" | 有意为之（§3.4）。不引入 `expired` 状态和相应的迁移 + 写入职责。 |
| 孩子能看到多个任务 | 和"一天只做一件事"有张力。靠视觉层级压制：主卡片全宽亮色，补做卡矮一半灰底，最多 2 张（§3.6）。 |
| 已完成任务仍能通过 URL 打开 | 只能看结算页，不能作答。三层防护，后两层是现成的（§3.8）。 |
