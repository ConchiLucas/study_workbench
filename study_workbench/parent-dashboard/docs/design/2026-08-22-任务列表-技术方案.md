# 任务列表（家长端）技术方案

> 版本 v1 · 2026-08-22 · 前置：`docs/design/2026-08-22-答题计划-技术方案.md`（每日答题计划 + iPad 答题端已上线）
> 目标：家长端有一个「任务列表」，能看到孩子每天的任务、点进去看这个任务包含哪 10 道题、每道题答得怎么样。

---

## 1. 这一版最重要的判断：不新建"任务"这个东西

需求描述的三件事——**每个任务能看要答哪些题**、**能看答题情况**、**每个任务量是大班一天的量**——后端 `study_plans` / `plan_items` 已经全部满足了。缺的只是家长端没有任何界面能点进去。

现状盘点：

| | `daily_tasks`（侧边栏「任务打卡」） | `study_plans` / `plan_items` |
|---|---|---|
| 内容 | 3 条 seed 写死的标题：「练 5 个算术知识点」等 | 每天 10 道真题，`question_id` 落库固定 |
| 和题目的关系 | **无任何关联**，`subject_id` 全是 NULL | 每题指向 `question_id` + `kp_id`，还带分桶原因 |
| 进度 | `done_count` 全代码库没有任何自动写入路径，只有家长手点「完成」一次性置为 `target_count` | 答一题自动累加，带对错、重试次数、单题耗时 |
| 量的依据 | 无 | `plan.DefaultQuota()` = 4+2+2+2，正是大班一天的量 |

所以方案是：**把 `study_plans` 以「任务」的名义暴露给家长端，废掉 `daily_tasks` 那套空壳。**

### 为什么不新建 `tasks` 表

新建表就得同时维护两份"今天要做什么"，而它们必然要保持一致（任务进度 = 计划进度）。一致性靠代码同步维护，迟早会不一致——`daily_tasks.done_count` 从来不涨就是现成的教训：表设计了进度字段，但没人负责写它。

### 命名上的取舍

**前端叫「任务」，后端表名和 API 继续叫 `plan`。** 不做重命名。

理由：改表名要动迁移、模型、8 个接口路径、孩子端全部调用、以及已上线的 `flower_ledger.ref_type='study_plan'` 历史数据。收益只是名字好看一点。代价和收益差得太远。

代价是留下一层"术语翻译"，所以在这里写清映射，后续看代码不用猜：

| 家长端叫法 | 代码里叫 |
|---|---|
| 任务 | `study_plan`（一天可有 1~3 份：主任务 + 加餐） |
| 任务里的一道题 | `plan_item` |
| 任务量 | `study_plans.target_count` |
| 任务状态 | `study_plans.status`：`pending` / `doing` / `done` |

## 2. 范围

### 做

1. **任务列表页**：按日期倒序列出任务，每条显示日期、主/加餐、进度、正确率、星星、用时、学科分布。
2. **任务详情**：点进去看这个任务的全部题目——题干、选项、哪个是正确答案、**孩子选了哪个**、对错、试了几次、单题耗时、这题为什么被选进来（复习/易错/在学/新知）。
3. **手动生成今天的任务**：孩子还没打开 iPad 时，家长可以先点一下把今天的任务生成出来，提前看今天要练什么。
4. **废弃 `daily_tasks`**：撤掉相关路由、前端页面和 seed 假数据；总览页的「今日任务」指标改为读任务（计划）份数。

### 不做（YAGNI）

- 家长手动组卷 / 指定题目 / 布置作业。这版任务仍然全自动生成，家长是**观察者**不是**出题者**。
- 改任务量、改分桶配额的界面。配额是 `plan.DefaultQuota()` 里的常量，要调先改代码。
- 删除任务、重做任务。任务是学习记录，删了就没有连续性，掌握度也对不上。
- 分页。一天最多 3 份任务，30 天不到 90 行，一次拉完。真到需要分页那天再说。

## 3. 任务量：大班一天该做多少

沿用上一版已经定下并跑通的口径，这里只做说明，不改动：

| 项 | 取值 |
|---|---|
| 每个任务题量 | **10 题**（复习 4 + 易错 2 + 在学 2 + 新知 2） |
| 单题时长 | 30~45 秒（含读题、思考、点选） |
| 任务总时长 | 6~8 分钟，控制在大班 8~12 分钟注意力窗口内 |
| 每天任务数 | 1 个主任务，家长可加餐，一天上限 3 份 |

**列表和详情必须显示 `done_count / target_count`，不能写死 `/10`。** 生成时如果候选知识点不够（题库快练完、或某学科题目缺失），`generate` 会把 `target_count` 修正成实际条数（`plan.go:205-209`）。写死 10 会让"8 题的任务做完了"显示成 8/10 永远不满。

## 4. 数据模型改动

只加一个字段。

### 迁移 `004_plan_picks`

```sql
-- postgres
ALTER TABLE plan_items ADD COLUMN picks VARCHAR(24) NOT NULL DEFAULT '';
```

```sql
-- sqlite
ALTER TABLE plan_items ADD COLUMN picks TEXT NOT NULL DEFAULT '';
```

**为什么需要它**：现在 `plan_items` 存了 `status` / `tries` / `cost_ms`，能告诉家长"这题错了、试了两次、花了 18 秒"，但**答不出"孩子当时选的是什么"**。而这恰恰是整个功能里最有诊断价值的一条信息——知道孩子把 `3+4` 选成 `8` 而不是选成 `2`，才看得出是"加法概念不会"还是"数错了一个"。少了它，"答题情况"就只是个红绿点。

**格式**：按作答顺序的选项下标，逗号分隔，如 `"3,1"` 表示第一次选了下标 3（错），第二次选了下标 1（对）。

- 为什么不用 JSON/JSONB：最多两个个位数整数。CSV 一行渲染即可，还省掉两个方言 JSON 类型的差异处理。
- 为什么不复用 `attempts`：`attempts` 表也没有存选项下标，一样要加列。而 `attempts` 是跨来源的通用表（`quiz` / 手动录入 / 导入），"选了第几个"只对选择题有意义，塞进去会让那张表变脏。
- 备选方案（未采纳）：给 `attempts` 加 `picked_index`，好处是家长端知识点抽屉里也能显示历史错选。但那是另一个功能的需求，等真要做时再加，两者不冲突。

**旧数据**：已经答过的历史任务 `picks` 是空串。前端要能降级——显示对错但不显示错选项，文案「早期记录未保存选项」。不做数据回填，`attempts` 里也没有这个信息，回填不出来。

### 写入点

`PlanService.Answer` 里已经有 `item.Tries++` 和 `Updates`（`plan.go:508-544`），在同一处追加：

```go
item.Picks = appendPick(item.Picks, in.OptionIndex)
```

一并进那个 `Updates` map。不新增查询、不新增事务。

## 5. 接口设计

### 5.1 任务详情（新增）

```
GET /api/v1/children/:cid/plans/:planId/review
```

**关键：这是一个和孩子端完全独立的 DTO，不能复用 `PlanDetail`。**

孩子端的 `QuestionDTO` 是刻意不含正确答案的（`plan.go:65` 有注释：判题在服务端做，孩子翻不到答案，掌握度数据才可信）。家长端**恰恰要看答案**。

如果给 `detail()` 加一个 `withAnswer bool` 参数，那么孩子端接口离泄题只差一个传错的布尔值。所以做成两个类型、两条代码路径，让"孩子拿到答案"在编译期就不可能：

```go
// service/plan_review.go

// ReviewQuestion 是家长端的题目视图，含正确答案。
// 和 QuestionDTO 分开定义而不是加开关：孩子端接口不该有任何路径能返回答案。
type ReviewQuestion struct {
	ID      int64           `json:"id"`
	Type    string          `json:"type"`
	Stem    string          `json:"stem"`
	Options json.RawMessage `json:"options"`
	Visual  json.RawMessage `json:"visual"`
	AnswerIndex int         `json:"answer_index"`
}

type ReviewItem struct {
	Seq         int    `json:"seq"`
	Status      string `json:"status"`       // pending|correct|wrong
	Bucket      string `json:"bucket"`       // review|shaky|learning|new
	Tries       int    `json:"tries"`
	CostMs      int    `json:"cost_ms"`
	Picks       []int  `json:"picks"`        // 按作答顺序，孩子选过的下标；旧数据为空
	AnsweredAt  *time.Time `json:"answered_at"`
	KpID        int64  `json:"kp_id"`
	KpTitle     string `json:"kp_title"`
	SubjectCode string `json:"subject_code"`
	SubjectName string `json:"subject_name"`
	Question    ReviewQuestion `json:"question"`
}

type PlanReview struct {
	Plan  PlanDTO      `json:"plan"`
	Items []ReviewItem `json:"items"`
}

func (s *PlanService) Review(childID, planID int64) (PlanReview, error)
```

实现：`loadPlan` 校验 `child_id` 归属（复用现成的，顺带防了越权读别人孩子的任务），然后一条 SQL——和 `detail()` 的那条几乎一样，多取 `q.answer`、`pi.picks`、`pi.cost_ms`、`pi.answered_at`。`q.answer` 用现成的 `parseAnswerIndex` 解成 `int`。

不复用 `detail()` 的 SQL 是有意的：为了省一条 20 行的查询而引入答案泄漏的可能，不值得。

错误码走现成的 `failPlan`：任务不存在或不属于该孩子 → 404。

### 5.2 任务列表（改造现有）

```
GET /api/v1/children/:cid/plans?from=&to=&status=
```

现有的 `History` 返回 `[]PlanDTO`，字段够用但少一样东西：**学科分布**。列表上一眼看到「算术×4 识字×3 古诗×3」，比只看到「10 题」有用得多。

不把 `Subjects` 加进 `PlanDTO`：`PlanDTO` 同时嵌在 `AnswerResult` 里，孩子端每答一题都会带上，白传。新加一层只给列表用的类型：

```go
type SubjectCount struct {
	Code  string `json:"code"`
	Name  string `json:"name"`
	Icon  string `json:"icon"`
	Count int    `json:"count"`
}

type PlanSummary struct {
	PlanDTO
	Subjects []SubjectCount `json:"subjects"`
}

func (s *PlanService) History(childID int64, from, to, status string) ([]PlanSummary, error)
```

学科分布用**一条聚合查询**取全部计划的，不是每条计划查一次（N+1）：

```sql
SELECT pi.plan_id, s.code, s.name, s.icon, COUNT(1) AS count
FROM plan_items pi
JOIN knowledge_points kp ON kp.id = pi.kp_id
JOIN modules m           ON m.id = kp.module_id
JOIN subjects s          ON s.id = m.subject_id
WHERE pi.plan_id IN ?
GROUP BY pi.plan_id, s.code, s.name, s.icon, s.order_no
ORDER BY pi.plan_id, s.order_no
```

`s.order_no` 必须写进 `GROUP BY`——Postgres 不允许 `ORDER BY` 用未分组的列（这个坑上一版在 subjects 查询上踩过一次）。

`status` 是新增的可选过滤（`pending`/`doing`/`done`），空则不过滤。`from`/`to` 保持现有默认（近 30 天）。

**破坏性变更**：返回类型从 `[]PlanDTO` 变成 `[]PlanSummary`。因为 `PlanSummary` 内嵌 `PlanDTO`，JSON 结构是向后兼容的（只多了 `subjects` 字段），前端现有的 `TodayPlanCard` 不用改也能跑。但 `History` 的 Go 签名多了一个参数，`listPlans` handler 和 `plan_test.go` 要跟着改。

### 5.3 生成今天的任务（新增）

```
POST /api/v1/children/:cid/plans/today
```

内部就是调现有的 `Plan.Today(childID)`（本来就是懒生成，没有就现场造）。

**为什么要一个显式接口，而不是列表页读的时候自动生成**：懒生成的原有理由是"家里的 iPad 不一定每天开机，定时任务只会造出一堆没人做的空计划，还会污染完成率统计"（`plan.go:91-92`）。家长每天打开一次列表页就自动建一份任务，等于把这个问题原样搬过来——家长只是看看，不代表孩子今天会做。

所以列表页只读，今天没有任务时显示一行占位 + 「生成今天的任务」按钮，家长主动点才建。

## 6. 前端

### 6.1 路由与导航

| 变更 | 前 | 后 |
|---|---|---|
| 侧边栏 | 📋 任务打卡 → `/calendar` | 📋 任务列表 → `/tasks` |
| 页面 | `CalendarPage`（假任务 + 热力图 + 趋势图） | `TasksPage`（任务列表 + 热力图 + 趋势图） |
| 新增 | — | `/tasks/:planId` 任务详情 |

`/calendar` 路由和 `CalendarPage` 删除，热力图和趋势图搬到 `TasksPage` 列表下方。它们本来就是"这段时间练了多少"，和任务列表是同一个主题，没必要占一个独立菜单。

保留 `/rewards` 奖励商店不动。

详情做成**独立路由页**而不是抽屉：10 道题带选项和图形，内容量撑不进抽屉；而且独立 URL 能分享、能刷新、能后退。

### 6.2 组件

```
frontend/src/pages/TasksPage.tsx          任务列表（含日期分组、状态筛选）
frontend/src/pages/TaskDetailPage.tsx     任务详情（10 道题的复盘）
frontend/src/components/task/TaskRow.tsx  列表里的一条任务
frontend/src/components/task/ReviewItemCard.tsx  详情里的一道题
frontend/src/api/plans.ts                 加 useTaskReview / useGenerateToday，History 加筛选参数
frontend/src/api/rewards.ts               从 tasks.ts 拆出 useRewards / useRedeem
```

**`ReviewItemCard` 的渲染要复用孩子端的 `QuestionVisual`**，不要重写一份。那个组件处理了 count/add/sub/shape/char/emoji/seq 七种图形（其中 `ShapeGlyph` 的 SVG 拼装不算简单），重写一份必然和孩子端漂移——孩子看到的图和家长看到的图不一样，这个功能就废了。

做法：给 `QuestionVisual` 加一个 `size?: 'kid' | 'compact'` prop，家长端传 `compact`。不担心打包：家长端页面本来就是 `React.lazy` 的，和 `/kid` 共享 chunk 不会让孩子端变大。

选项渲染**不**复用 `OptionButton`——那个组件带点击态、动画、音效回调，家长端是只读展示，直接写一个静态的选项行更简单。每个选项标注三种态：正确答案（绿框 ✓）、孩子选过的错选项（红框 ✗）、其余（灰）。

### 6.3 列表页显示什么

按日期倒序分组，每组一个日期标题（今天/昨天/`8月20日`）。组内每条任务一行：

- 标签：`seq_no === 1` → 「今天的练习」/「练习」，否则 「加餐 N」
- 学科 chip：`🔢 算术 4`、`📖 识字 3`
- 进度条：绿色 = 答对，玫红 = 答错，灰 = 未答（复用 `TodayPlanCard` 已有的堆叠条写法）
- `8/10 · 正确率 75% · 4 分钟 · ⭐⭐`
- 未开始的任务显示「还没开始」，进度条全灰

今天没有任务时，列表顶部一行占位 + 「生成今天的任务」按钮。

### 6.4 详情页显示什么

顶部任务概要卡（日期、状态、进度、正确率、用时、星星、小红花），下面 1~10 逐题：

每题一张卡：序号 + 学科 + 知识点标题 + **分桶徽章**（复习 / 易错 / 在学 / 新知）+ 状态徽章（✓ 一次答对 / ✓ 第二次答对 / ✗ 没答对 / 未作答）+ 耗时。然后是图形区 + 题干 + 四个选项（按上面的三态标注）。

**分桶徽章值得单独强调**：`plan_items.bucket` 记录了这题当初为什么被选进来。家长看到「这题是『易错』桶里的，又答错了」，比看到一个孤立的红叉信息量大得多，而这个字段现有 DTO 里已经有了，白拿。

底部一行汇总：这次任务里错的题都属于哪些知识点，链到 `/subjects/:code`。

- `TestHistorySubjectCountsMatchTarget`：学科分布数量之和等于 `target_count`
- `TestHistoryStatusFilter`：`status=done` 只返回已完成的
- `TestGenerateTodayIsIdempotent`：连调两次 `POST /plans/today`，当天只有一份 seq_no=1

**前端**：`npm run build` + `tsc` 通过；浏览器走查列表页和详情页，重点确认七种 `visual.kind` 在 `compact` 尺寸下都不错位，以及 `/kid` 流程没被 `QuestionVisual` 改动影响。

## 10. 已知取舍和风险

| 项 | 说明 |
|---|---|
| 前后端术语不一致 | 前端「任务」= 后端 `plan`。已在 §1 写明映射表。代价是新人看代码要转一次，但比重命名 8 个接口 + 迁移历史数据划算。 |
| 家长端能看到未做任务的答案 | `Review` 对 `pending` 任务也返回答案。如果孩子拿家长的设备翻列表，理论上能提前看答案。判断为可接受：家长端和孩子端是不同入口、不同视觉风格，5 岁孩子不会主动去翻 `/tasks/:id`。真要防，等有登录态了再加。 |
| 旧任务没有 `picks` | 历史记录只能显示对错，不能显示错选项。前端降级文案说明。不回填——`attempts` 里也没这个信息。 |
| 不能删除/重做任务 | 有意为之。任务是学习记录，删掉会让掌握度和连续天数对不上。 |
| 无分页 | 一天最多 3 份，默认查近 30 天 ≤ 90 行。真到需要分页时列表已经先该做归档了。 |
| `QuestionVisual` 被两端共用 | 改它会同时影响家长端和孩子端。这是有意选的——两边显示不一致的 bug 比"改动要同时验证两处"更难查。第 7 步的走查必须覆盖 `/kid`。 |
